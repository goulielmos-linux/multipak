# Como o MultiPak instala pacotes do Alpine Linux

*MultiPak 1.1.0.*

---

## 1. Explicação simples

### 1.1 O que é um pacote `.apk` do Alpine?

O Alpine Linux é uma distribuição muito pequena (a imagem oficial tem uns 4 MB), por
isso muito usada como base de contêineres em servidores. Ele usa a biblioteca C **musl**
em vez da glibc, então seus programas só rodam num Alpine. O gerenciador de pacotes é o
**apk**, e um pacote `.apk` (formato clássico, "v2") é uma sequência de dois ou três
arquivos gzip colados: a assinatura (opcional), a ficha `.PKGINFO` e os arquivos do
programa.

Não confundir com o `.apk` do **Android**, que é um arquivo ZIP: o MultiPak percebe a
diferença pelo conteúdo e instala o aplicativo Android pelo Waydroid.

### 1.2 O que o MultiPak faz?

1. **Lê sem executar:** lê só a ficha `.PKGINFO`. Nada é extraído.
2. **Distingue do Arch:** o `.PKGINFO` do Alpine tem o mesmo formato do Arch Linux.
   O MultiPak olha a assinatura `.SIGN.*` ou os campos `origin` e `datahash`.
3. **Estima a release:** a primeira linha do `.PKGINFO` diz qual versão do *abuild*
   (a ferramenta de compilação do Alpine) fez o pacote, e cada release do Alpine usa a
   sua. Num teste com cerca de 800 pacotes reais, isso acertou o ramo em quase todos.
4. **Sugere o ambiente:** a release estimada; se ela já saiu de suporte, é oferecida
   mesmo assim, com um aviso (o pacote precisa das bibliotecas dela); se for mais nova
   que as estáveis, o ramo de desenvolvimento (*edge*).
5. **Instala com o apk:** num contêiner `MultiPak-Alpine-<release>` feito da imagem
   oficial (poucos MB). As dependências vêm dos repositórios do Alpine.
6. **Atalho no menu.**

Pacotes assinados pelo Alpine passam pela verificação normal. Os que não têm essa
assinatura, como os compilados localmente ou vindos de terceiros, são instalados sem a
verificação, **com um aviso**.

### 1.3 O contêiner

- Um ambiente por release suportada no dia (em novembro de 2026: 3.24, 3.23, 3.22) e
  o *edge*. A lista vem do registro de imagens e do calendário oficial de suporte.
- O Distrobox conhece o apk e prepara o contêiner sozinho.
- Antes de cada instalação, o MultiPak adiciona as traduções (no Alpine elas vêm em
  pacotes `-lang` separados, que passam a entrar sozinhos com cada programa) e segue o
  tema claro ou escuro do computador no GTK 3.

### 1.4 Atualizar e remover

- **Atualizar**: em **Gerenciador → Atualizar**, o MultiPak atualiza o contêiner inteiro
  com o comando do próprio Distrobox (`distrobox upgrade`), que usa o apk.
- **Versões novas**: o Gerenciador consulta `apk version` para saber quais aplicativos
  têm versão nova e mostra cada um em **Com atualização**, **Em dia** ou **Sem fonte de
  atualização** (instalado de um arquivo que nenhum repositório oferece). Ao abrir, usa
  a lista que o contêiner já tem, sem baixar nada; **Verificar atualizações** antes roda
  `apk update`.
- **Remover**: o `apk del` não remove um pacote de que outros dependem, mas termina
  "com sucesso". O MultiPak confere antes e explica quem depende dele. O `apk del`
  remove também as dependências órfãs e as traduções do programa.

### 1.5 O que (ainda) não funciona

- Formato **apk v3** (novo, binário): recusado com mensagem clara (os repositórios do
  Alpine ainda publicam v2).
- Pacotes feitos para outra release podem não achar uma biblioteca (o apk avisa).
- Só x86-64 e `noarch`.
- Pacotes sem a linha do abuild (ex.: feitos com melange/Wolfi) ficam com a estável
  mais nova e confiança "Média".

## 2. Explicação técnica

Caminhos de código são relativos a `src/multipak`.

### 2.1 Visão geral dos módulos

| Módulo | Papel |
| --- | --- |
| `alpine.py` | leitor v2, `is_candidate`, `is_v3`, tabela abuild → release, fim de suporte |
| `metadata.py` | detecção antes do Arch; dica `alpine-<release>` |
| `models.py` (`alpine_environment`, `ALPINE_ENVIRONMENTS`) | ambientes e fallback offline |
| `catalog.py` (`alpine_profiles`, `alpine_package_environment`) | releases do dia e escolha |
| `environments.py` (`release_identity`), `alpine.release_version` | `3.24.3` → `3.24`, `_alpha` → `edge` |
| `engine.py` (`_install_apk`) | `apk verify`, preparo e `apk add` |
| `assets/alpine-setup.sh` | `--prepare`: GTK 3 e `lang` + `musl-locales` |
| `guest.py` (`alpine_records`, `alpine_dependents`) | estado, arquivos e recusa de remoção |
| `suggestions.py` | confiança Alta/Média e nota do musl |
| `assets/multipak-alpine.xml` | MIME `application/x-alpine-package` (`*.apk`, marca inicial (*magic number*) do gzip) |

### 2.2 Leitura, sem executar

Os segmentos gzip são lidos em sequência com `tarfile` em modo *stream* (os TAR do
abuild não têm marca de fim). Só o `.PKGINFO` é lido. A marca inicial
`ADB.`/`ADBd`/`ADBc` (v3) gera `alpine.v3_error()` antes de qualquer leitura; um ZIP com
sufixo `.apk` segue para o caminho do Android (`android_bundle.inspect_android`).

### 2.3 Estimativa da release

`# Generated by abuild 3.N.x` → release: tabela medida (3.4→3.10 … 3.9 final→3.16) e,
a partir de 3.10, *minor* + 7 (3.17→3.24, 3.18→3.25). `builddate` foi descartado (é a
data do commit do APKBUILD). Sem a linha, não há dica.

### 2.4 Catálogo e escolha

- `alpine_profiles`: tags `3.N` de `skopeo list-tags docker://docker.io/library/alpine`
  ainda suportadas segundo `https://alpinelinux.org/releases.json` (lido a cada
  atualização do catálogo, com a tabela `alpine.END_OF_SUPPORT` de reserva), mais
  `edge` por último. Sem rede: cache ou `ALPINE_ENVIRONMENTS`.
- `alpine_package_environment`: release exata se listada; release sem suporte é
  oferecida mesmo assim (e entra antes do edge na lista avançada); mais nova que todas
  as estáveis → edge.
- Confiança (`suggestions.py`): **Alta** quando a estimativa bate (com aviso se a
  release não tem mais suporte); **Média** para o edge ou sem estimativa.

### 2.5 Instalação (`engine._install_apk`)

1. `sudo apk update`.
2. `alpine-setup.sh --prepare`: `/etc/xdg/gtk-3.0/settings.ini` com `prefer-dark`
   conforme o host; `apk add lang musl-locales` (com `lang`, os `<nome>-lang` entram
   por `install_if`).
3. `apk verify --quiet <arquivo>`; se falhar, `--allow-untrusted` + aviso.
4. `sudo apk add [--allow-untrusted] <arquivo>`.

A barra de progresso segue as linhas `( 1/78) Installing` (`container_progress.py`).

### 2.6 No contêiner (`guest.py`)

`/lib/apk/db/installed` é lido em registros (`P:` nome, `F:`/`R:` arquivos, `D:`
dependências, `p:` o que fornece). Dependente = quem tem em `D:` o nome do alvo ou algo
do `p:` dele (como `so:libgtk-3.so.0`). Com dependentes, a remoção é recusada; senão
`apk del --no-progress nome`.

### 2.7 Contêiner existente

`release_identity` normaliza o os-release: `VERSION_ID=3.24.3` → `3.24`;
`3.25.0_alpha…` → `edge`. Um contêiner só é reaproveitado se a release bater.

### 2.8 Diferenças em relação ao uso normal

| Assunto | Alpine de verdade | MultiPak |
| --- | --- | --- |
| Pacote sem chave confiável | `--allow-untrusted` à mão | automático, com aviso |
| Traduções | instalar `lang` à mão | `lang` + `musl-locales` antes de cada instalação |
| `apk del` com dependentes | sai 0 sem remover | recusa com explicação |
| Release | a do sistema | a estimada pelo abuild |

### 2.9 Onde olhar quando algo dá errado

- `~/.local/share/multipak/installations/<id>/installation.log`.
- `distrobox enter MultiPak-Alpine-3.24 -- apk info -vv`.
- Biblioteca faltando: escolha na lista avançada a release para a qual o pacote foi
  feito.
